# Username Scan Agent Guide

## Project Summary

Username Scan is a Next.js application for checking username availability across selected social, creator, and gaming platforms. The current app favors reliable official APIs and stable public endpoints over scraper-heavy checks.

Production site: `https://usernamescan.com`

## Tech Stack

- Next.js App Router `16.2.6`
- React `19.2.6`
- TypeScript
- Tailwind CSS v4 through `@tailwindcss/postcss`
- `lucide-react` for UI icons
- `nodemailer` for SMTP contact-form delivery
- Node.js route handlers on Vercel
- In-memory cache and rate limiting for v1

## Repository Layout

- `src/app`: App Router pages, layouts, sitemap, and API route handlers.
- `src/app/api/check/route.ts`: Username availability API.
- `src/app/api/contact/route.ts`: Contact/platform-request API backed by SMTP.
- `src/components/search-interface.tsx`: Client-side username search UI.
- `src/components/contact-form.tsx`: Client-side contact form.
- `src/lib/platforms.ts`: Platform registry, validation notes, active/inactive status, and result types.
- `src/lib/checkers.ts`: Platform-specific availability checks and token handling.
- `src/lib/check-cache.ts`: In-memory checker result cache.
- `src/lib/rate-limit.ts`: In-memory fixed-window rate limiter.
- `tests/platforms.test.ts`: Registry and rate-limit unit tests.
- `public/img`: Platform icons.
- `public/robots.txt` and `public/ads.txt`: Search and ad platform files.

## Routes

- `GET /`: Homepage and username checker UI.
- `GET /api/check?username=example`: Runs active platform checks and returns JSON.
- `POST /api/contact`: Sends contact/platform-request submissions through SMTP.
- `GET /contact`: Contact page with client form.
- `GET /platforms`: Platform coverage index.
- `GET /platforms/[slug]`: Static platform detail pages.
- `GET /about`: About page.
- `GET /privacy`: Privacy policy page.
- `GET /terms`: Terms page.
- `GET /sitemap.xml`: Generated by `src/app/sitemap.ts`.
- `GET /robots.txt`: Served from `public/robots.txt`.

## Data Flow

### Username Search

1. `src/app/page.tsx` renders the homepage and passes active platforms into `SearchInterface`.
2. `SearchInterface` submits `GET /api/check?username=...` and stores the query in the URL.
3. `src/app/api/check/route.ts` rate-limits by client IP, validates the username length, and calls `checkUsername`.
4. `src/lib/checkers.ts` normalizes the username, validates it per platform, checks the in-memory cache, and runs active platform checkers in chunks of four.
5. Platform checkers call official APIs or stable public endpoints with a 4-second timeout.
6. Results are cached for 6 hours, capped at 1000 entries, and returned as JSON.

`GET /api/check` response shape:

```ts
type CheckResult = {
  platform: string;
  status: "available" | "taken" | "invalid" | "unknown" | "auth_failed" | "disabled";
  profileUrl?: string;
  reason?: string;
  reliability: "official_api" | "public_endpoint" | "disabled";
  checkedAt: string;
};
```

### Contact Form

1. `src/app/contact/page.tsx` renders `ContactForm`.
2. `ContactForm` posts JSON to `POST /api/contact`.
3. `src/app/api/contact/route.ts` rate-limits by client IP, validates required fields and max lengths, verifies SMTP configuration, and sends an email through Nodemailer.
4. If SMTP variables are missing, the route returns `503` and logs a warning.

## Environment Variables

Copy `.env.example` to `.env.local` for local development and fill in real values.

Required for full production functionality:

```text
STEAM_API_KEY
TWITCH_CLIENT_ID
TWITCH_CLIENT_SECRET
REDDIT_CLIENT_ID
REDDIT_CLIENT_SECRET
TUMBLR_CONSUMER_KEY
SMTP_SERVER
SMTP_PORT
SMTP_USERNAME
SMTP_PASSWORD
SMTP_FROM_EMAIL
SMTP_TO_EMAIL
```

Optional:

```text
GITHUB_TOKEN
NEXT_PUBLIC_ADSENSE_CLIENT
```

Notes:

- `GITHUB_TOKEN` is optional. GitHub checks still run anonymously, but the token helps avoid anonymous API rate limits.
- Missing Steam, Twitch, Reddit, or Tumblr credentials cause those platform checks to return `auth_failed`.
- Missing SMTP variables make `/api/contact` return `503`.
- `NEXT_PUBLIC_ADSENSE_CLIENT` injects the Google AdSense script from `src/app/layout.tsx`.
- Do not commit real `.env` or `.env.local` files.

## Vercel Deployment

1. Push the repository to GitHub.
2. Import the project into Vercel as a Next.js app.
3. Use the repository root that contains `package.json`.
4. Keep the default install/build settings unless the project structure changes:
   - Install command: `npm install`
   - Build command: `npm run build`
   - Output: Vercel-managed Next.js output
5. Add the environment variables listed above in Vercel Project Settings.
6. Deploy.
7. Add or verify the production domain `usernamescan.com`.
8. After deployment, smoke test:
   - `GET /`
   - `GET /platforms`
   - `GET /api/check?username=example`
   - `GET /contact`
   - `POST /api/contact` with valid SMTP configuration

## Runtime Behavior

- `/api/check` rate limit: 5 requests per minute per IP.
- `/api/contact` rate limit: 3 requests per hour per IP.
- Rate limits are in memory and reset per serverless instance.
- Checker cache is in memory, 6-hour TTL, 1000-entry cap.
- Active checker concurrency cap: 4.
- Outbound checker timeout: 4 seconds.
- Upstream failures return `unknown`, not `available`.

## Known Issues

### High Severity: Nodemailer `raw` Option Alert

The project currently depends on `nodemailer@8.0.8`, and a prior audit flagged a HIGH-severity Nodemailer issue involving SSRF or arbitrary file read through the `raw` message option.

This documentation update does not fix the dependency alert.

Current code findings:

- `src/app/api/contact/route.ts` imports Nodemailer and calls `transporter.sendMail`.
- The current route does not pass a `raw` option to `sendMail`.
- User-controlled contact fields are assembled into the `text` email body after basic length validation.
- `POST /api/contact` is publicly reachable in production on Vercel because it is an App Router API route with no auth or middleware gate.
- `/contact` is also publicly reachable and linked from the site footer.
- If SMTP environment variables are missing, `/api/contact` returns `503`, but the route still exists.

Until this is remediated, do not add or expose any `raw` option in the contact route, and do not pass user-controlled input into Nodemailer transport or message options beyond the existing validated text body. Treat the alert as unresolved until Nodemailer is upgraded or a documented mitigation is applied.

### Operational Follow-Ups

- Replace in-memory cache and rate limiting with shared storage such as Redis if traffic grows or stricter enforcement is needed across serverless instances.
- Add CAPTCHA or another abuse-control mechanism to the contact form before heavy production use.
- Add browser or end-to-end tests for the username search and contact flows.
- Add the real Google AdSense publisher line to `public/ads.txt` only after AdSense approval.
